# Agent Sandbox 技术 - STAR 总结

> 调研日期：2026-02-28

---

## STAR 方法论概述

STAR 是一种结构化总结方法，包含四个部分：
- **S**ituation（背景 + 痛点）
- **T**ask（核心问题）
- **A**ction（主流方案）
- **R**esult（效果 + 建议）

---

## Situation（背景 + 痛点）

**字数：约 150 字**

随着 LLM 代码执行能力成为标准功能（如 Code Interpreter），AI Agent 可以直接生成并执行代码。这带来了严峻的安全挑战：**LLM 可能生成恶意代码**（被注入攻击）、**错误代码**（如 rm -rf /）或**资源耗尽代码**（无限循环）。传统安全防护无法应对动态生成的代码风险，需要专用沙箱技术。

**核心痛点提炼**：
1. LLM 生成代码不可预测
2. 传统安全无法动态响应
3. 需要平衡安全与性能
4. 多租户场景隔离要求高

---

## Task（核心问题）

**字数：约 100 字**

Agent Sandbox 需要解决的关键问题是：**如何在支持开放式代码执行的同时，确保主机系统和数据的安全**。核心约束包括：启动延迟 (<1s)、性能损耗 (<20%)、隔离强度 (防止逃逸)、并发支持 (>100 实例)、易用性 (开发者友好)。

**核心问题拆解**：
1. 隔离强度 → 容器 vs VM vs 微 VM
2. 资源限制 → CPU/内存/网络/磁盘
3. 安全审查 → 执行前/执行中检测
4. 监控审计 → 日志记录、异常检测

---

## Action（主流方案）

**字数：约 150 字**

技术演进历经三代：**第一代**（Docker 容器）提供基础隔离但强度有限；**第二代**（gVisor/Firecracker）引入系统调用过滤和微 VM，平衡安全与性能；**第三代**（E2B/OpenHands）专为 AI Agent 设计，内置安全策略和监控。核心突破包括：seccomp 自动配置、微 VM 冷启动优化、多层防御架构。

**技术演进关键点**：
| 代际 | 代表技术 | 核心贡献 | 局限性 |
|------|---------|---------|--------|
| 第一代 | Docker | 容器普及，轻量隔离 | 逃逸风险，共享内核 |
| 第二代 | gVisor/Firecracker | 系统调用过滤，微 VM | 配置复杂，性能损耗 |
| 第三代 | E2B/OpenHands | AI 场景优化，内置监控 | 商业依赖，定制有限 |

---

## Result（效果 + 建议）

**字数：约 100 字**

当前沙箱技术可支持 99%+ 的安全代码执行场景，启动延迟<500ms，性能损耗<15%。但仍有**侧信道攻击**、**0-day 逃逸**、**供应链攻击**等风险。实操建议：**低风险用 Docker**，**AI 场景用 E2B/OpenHands**，**高风险用 Firecracker/gVisor**，并始终启用**执行超时**、**资源限制**和**安全审查**。

**核心指标**：
| 指标 | 当前水平 | 目标值 |
|------|---------|--------|
| 启动延迟 | <500ms | <200ms |
| 性能损耗 | <15% | <5% |
| 隔离强度 | 阻止 99%+ 已知逃逸 | 100% |

**选型建议速查**：
| 场景 | 推荐方案 | 理由 |
|------|---------|------|
| 开发测试 | Docker | 快速，生态好 |
| AI Agent | E2B/OpenHands | 专用优化 |
| 多租户 | gVisor/Firecracker | 强隔离 |
| 企业级 | Kata/Firecracker | VM 级安全 |
